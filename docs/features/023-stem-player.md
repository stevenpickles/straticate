# [023] Stem player UI (synchronized playback, solo, mute, seek)

Branch: `023-stem-player`
Status: PR OPEN
Dependencies: 017, 021
PR: #26

## Objective

A completed job's stems can be listened to. All of a job's stems play in
sample-accurate sync off one audio clock, each with its own mute and solo, with
play/pause, a seek scrubber that keeps them locked together, and a playhead
readout derived from the audio clock. This is what makes the fake separator's
output inspectable and closes the second-to-last gap in milestone M1.

## Scope

- `frontend/src/audio/engine.ts` — the Web Audio engine, deliberately free of
  React: fetch → `decodeAudioData` per stem, one `GainNode` per stem, a single
  scheduled start time and offset shared by every source, seek by recreating
  the sources together, pause/resume, an audio-clock playhead, and disposal.
  Exposes a `subscribe`/`getSnapshot` pair so any React component can read it
  through `useSyncExternalStore`, and takes both its `AudioContext` and its
  byte loader as injectable factories.
- `frontend/src/components/StemPlayer.tsx` (+ `.css`) — one row per stem of
  `SeparationResult.stems`, each with Mute and Solo; transport with play/pause,
  a range scrubber and a `current / duration` readout using the existing
  `formatDuration`; loading, decoding and the error states feature 021
  documents for these routes.
- `frontend/src/api/stems.ts` — `stemUrl()`, `getSeparationResult()` and
  `fetchStemAudio()`, all with the project's `ApiError` envelope handling.
- Phase scaffolding for **024**: an `inspect` branch in `Workspace.tsx`
  mounting `<StemPlayer />` and `<ExportPanel />`; `ExportPanel.tsx` (+ `.css`)
  as a minimal placeholder handed to 024; the `results/inspect` and
  `results/startAnother` actions in `state/appState.tsx`; and the "View
  results" and "Start another separation" buttons on the terminal states of
  `SeparationProgress.tsx`.
- `frontend/src/test/fakeAudioContext.ts` — a recording fake of the slice of
  the Web Audio API the engine uses, shared by the engine and component tests.

## Acceptance criteria

- [x] Stems are rendered from `result.stems`; a two-stem and a four-stem job
      both work; no stem name or count is hardcoded in any production module.
- [x] All stems start from a single scheduled start time off one clock, so they
      stay in sync; seeking restarts them together at the new offset.
- [x] Mute and solo behave correctly, including multiple solos and clearing
      solo back to the prior mute state.

      cancelled/failed via `detail.state`) and `stem_file_missing` (404) each

## Notes / decisions

### PR review findings (PR #26)

Seven findings, all fixed in-branch with regressions that fail against the code
as first written.

1. **Scrubbing rebuilt the source graph on every input event.** React's
   `onChange` on `<input type="range">` *is* the native `input` event, so it
   fires continuously while dragging; seeking on each one stopped, discarded
   and recreated every source dozens of times a second, each rebuild opening a
   fresh 50 ms lookahead — audible gapping, not scrubbing. The drag now moves
   only the displayed value and the seek is **committed once, on release**
   (`pointerup`/`mouseup`/`keyup`/`blur`). A ref that clears synchronously
   makes a pointerup and its mouseup one seek, the same idiom 011 and 017 use
   for double-submit.
2. **The `inspect` phase was a dead end.** "Start another separation" lived
   only on `SeparationProgress`, which is mounted for `separate` alone, so
   opening the results stranded the user until a page reload — contradicting
   this feature's own acceptance criterion. The control now also lives in
   `StemPlayer`, outside its body switch, so it is present in the loading,
   error and playable states alike. `Workspace.test.tsx` walks the whole round
   trip (complete → view results → start another → configure) through the real
   components and reducers.
3. **A transient `resume()` failure stuck forever.** An autoplay-policy
   rejection was written to the engine's single `error` field and nothing ever
   cleared it, so the banner outlived the click that fixed it. The engine now
   separates `transportError` (cleared by the next `play()`) from `loadError`
   (no remedy but another load); the snapshot shows the transport failure while
   it stands and falls back to the load failure — so a missing stem is *not*
   erased by a successful retry.
4. **`load()` and `play()` could reject**, against their documented contract
   and the `void instance.load(...)` the component relies on: the post-`await`
   graph wiring and `startSources` were outside any `try`, and a context the
   browser closed (tab discard, memory pressure) throws there. Both now catch
   and land the failure in the snapshot; `seek()` and `stopSources()` too.
5. **`dispose()` left downloads running.** A stem is a whole audio file, so a
   four-stem teardown leaked four full transfers — twice over under React
   StrictMode's double-invoked mount effect. `fetchStemAudio` takes an
   `AbortSignal`, the engine threads one through `loadStemAudio`, and both
   `dispose()` and a superseding `load()` abort it.
6. **`load()` was not re-entrancy-safe.** It reassigned `this.entries` up
   front, then wired the *first* call's buffers onto the *second* call's
   entries after the await. It is now generation-guarded — entries held in a
   local, results published only while no later load has started — and tears
   down the previous graph instead of orphaning its gain nodes.
7. **`startAnother` dispatched to two stores with mismatched guards.**
   `job/clear` always applied while `results/startAnother` was a no-op without
   an uploaded file, which would clear the job while leaving the phase behind —
   another unrecoverable state. The reducer now always transitions, falling
   back to `select` when there is no file to configure.

### Why the engine is not a hook

The Web Audio graph is a long-lived, imperative, mutable object with a clock.
Modelling it as React state would mean re-rendering at 60 Hz and re-deriving
node identity on every render. Instead `StemAudioEngine` is a plain class that
owns the graph and publishes an immutable snapshot through
`subscribe`/`getSnapshot`, which `useSyncExternalStore` consumes. Three
consequences, all deliberate:

1. it is unit-testable with no DOM and no React at all;
2. feature 024 (or anything later) can reuse it without inheriting this
   component's markup;
3. the snapshot is the only thing React ever sees, so a render never reaches
   into the audio graph.

### What makes it testable: two injected factories

jsdom implements **no** Web Audio API — no `AudioContext`, no
`decodeAudioData`, no `AudioBufferSourceNode`. So the engine takes:

- `createContext?: () => AudioEngineContext`, defaulting to
  `new AudioContext()`, and
- `loadStemAudio?: (url) => Promise<ArrayBuffer>`, defaulting to the typed stem
  client.

`AudioEngineContext` and friends are **structural subsets** of the real
interfaces, declaring only what the engine touches. A real `AudioContext` is
assignable to them with no cast (the compiler is what proves it), and
`test/fakeAudioContext.ts` implements the same shape while recording every
scheduled start time, offset, gain value and connect/disconnect. Tests then
assert on **what was scheduled**, never on audible output.

The context is built lazily, on the first `load()`, rather than in the
constructor: constructing an engine must never require a browser.

### One clock reading, not one per stem

`startSources(offset)` reads `context.currentTime` **once**, before the loop,
and passes the same `when` and the same `offset` to every source's `start()`.
Reading the clock again inside the loop — or calling `start()` with no
argument — would smear the stems apart by however long node creation took,
which is the difference between "sample-accurate" and "started at about the
same time". The lookahead (50 ms by default) exists so every source is created
and connected before the shared start time arrives.

An `AudioBufferSourceNode` is single-use, so **seeking is the same operation
again**: stop and discard the running sources, create a fresh set, and start
them together at one new time with one new offset. The tests assert exactly
that — one distinct `when` and one distinct `offset` across the whole new
generation.

### The playhead comes from the audio clock

`currentTime()` is `startOffset + (context.currentTime - scheduledStart)`,
clamped to `[0, duration]`, or the stored position while paused. It is never a
counter incremented by a timer, which would drift away from what is actually
audible. Animation frames only decide how often the readout is *repainted*;
the value they read is always the clock's. Pausing cancels the frame loop
rather than freezing a counter, and a seek writes the readout directly.

### Solo wins over mute

Any solo silences every non-soloed stem; solos are additive; and a soloed stem
is heard even if it is also muted, so clearing the last solo restores exactly
the mute state the user had before — the behaviour a DAW mixer has. All three
rules live in one function (`applyGains`) and are pinned by tests both at the
engine level and end to end through the UI.

### The result is fetched, not read off the job record

`job.result` is already in the store by the time the `inspect` phase renders,
but the player calls `GET /jobs/{id}/result` anyway. That route is the
contract's source of truth, and it is the only thing that can say *why* there
is nothing to play: a `409 result_not_available` carries the job's `state` in
`detail`, which the component turns into "still separating", "you cancelled
this" or "this failed" (feature 021's design — one code, one `detail` field,
no second branch for every client). A `404 stem_file_missing` while loading the
audio means the job record outlived its files, so the message offers a re-run
rather than a retry.

### A missing stem does not silence the rest

If one stem fails to load, the engine stays `ready` with the stems that
decoded, marks the failed one `error`, and surfaces the first failure on the
snapshot. The player then shows the remaining stems *and* an alert, and
disables that row's Mute/Solo. Only a job where nothing loaded is `error`.

### The routes out of `separate` are claimed here

011 and 017 both flagged "there is no way back from `separate` to `configure`"
as unclaimed. This feature claims it, minimally:

- `results/inspect` (from `separate` only) advances to `inspect`, dispatched by
  a "View results" button on the completed state;
- `results/startAnother` returns to `configure` with the upload, the loaded
  catalog and the selection intact and any stale create error cleared,
  dispatched by a "Start another separation" button on **every** terminal state
  together with a `job/clear` on the job store.

Both rules live in the reducer (and are unit-tested there) rather than in the
component, following 011's precedent. `SeparationProgress` now needs an
`AppStateProvider` above it; its progress, cancel and terminal logic is
otherwise untouched.

## Known limitations

- **No per-stem volume UI.** The engine supports `setLevel(name, 0..1)` and it
  is tested, but nothing in the UI drives it — the assignment scoped volume
  automation out. A future feature can add faders with no engine change.
- **Whole stems are downloaded before playback.** The engine fetches and
  decodes each stem in full, so a long job takes a moment to become playable.
  The backend already supports `Range` (021), so a streaming/progressive
  decode is possible later; it is not needed for the fake separator's short
  fixtures and would have meant writing a chunk scheduler.
- **No per-stem load progress.** Each stem is `loading` until it is `loaded`
  or `error`; there is no byte-level progress bar.
- **The playhead does not survive a phase change.** Leaving `inspect` disposes
  the engine, so returning starts from zero and re-downloads the stems.
- **The scrubber commits on release, not continuously.** That is what stops the
  source graph being rebuilt per input event, but it also means there is no
  scrub-while-playing preview: the audio jumps once, when the pointer is let
  go. A preview would need a separate short-lived source, which is out of scope
  here.
- **`stem_not_found` is not specially phrased.** The player only ever asks for
  stems the result listed, so that code cannot occur here; it falls through to
  the envelope's own message.
- **No keyboard shortcuts** (space to play/pause, arrow-key scrubbing). The
  scrubber is a real range input, so arrow keys move it natively, but there is
  no global transport binding.
